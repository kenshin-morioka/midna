# 0004 - ツール実行は Ollama の tool calling に乗せる

- 状態: 採択
- 日付: 2026-07-05
- 決定者: kenshin-morioka

## 結論

「LLM にどのツールを使わせるか」の判断は、Ollama が提供する tool calling（OpenAI 互換の function 形式）に任せる。リクエストにツール定義（`tools`）を渡し、応答の `tool_calls` を Midna 側で実行して、結果を `role: tool` のメッセージとして返す。

## 背景

エージェントがツールを使うには、LLM の出力から「どのツールをどの引数で呼ぶか」を取り出す必要がある。その取り出し方を決める。

判断の軸:

- 引数の取り出しが壊れにくいこと
- 実装とプロンプトの手間が小さいこと
- provider を差し替えたとき（[ADR 0003](0003-provider-abstraction-from-v0.md)）に持ち越せる形であること

## 理由

- Ollama がモデル側の学習済みフォーマットで構造化してくれるので、自前のテキスト解析より壊れにくい
- OpenAI 互換の形式なので、将来他の provider に差し替えても同じ抽象（`ToolSpec` / `ToolCall`）をほぼそのまま使い回せる
- プロンプトに「JSON で返して」といった指示を書き足す必要がなく、システムプロンプトを汚さない

## 影響

- メリット
  - ツールの追加が「定義 + 実行本体」を書くだけで済む
  - 引数が JSON として渡ってくるので、検証がシンプル
- デメリット
  - tool calling に対応したモデルしか使えない（llama3.1 / qwen2.5 など。対応していないモデルではツールが呼ばれない）
  - `Message` に `tool_calls` と `role: tool` という Ollama 由来の形が入り、wire format が provider 抽象に少し漏れる

## 他に検討した案

- **プロンプトで「JSON を返して」と指示して自前で解析する** — どのモデルでも動くが、出力が崩れたときの解析が壊れやすく、プロンプトの維持コストも高いため不採用。
- **ReAct 形式（Thought / Action / Observation のテキスト規約）** — 同じく解析が壊れやすい。tool calling が使える環境であえて選ぶ理由がないため不採用。

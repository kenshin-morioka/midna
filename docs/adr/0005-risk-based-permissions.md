# 0005 - ツールの権限は危険度で決め、状態を変える操作は毎回確認する

- 状態: 採択
- 日付: 2026-07-05
- 決定者: kenshin-morioka

## 結論

ツールに危険度（`Risk`: ReadOnly / Write / Execute）を持たせ、権限はツール名ではなく危険度で判定する。読むだけの操作は自動許可、ファイル書き込みとコマンド実行は実行前に毎回 y/N で確認する。拒否はエラーで落とさず「拒否された」という結果として LLM に返す。

## 背景

エージェントが勝手にファイルを壊したりコマンドを実行したりしない仕組みが要る。一方で、読むだけの操作まで毎回確認すると使い物にならない。どの粒度で何を確認するかを決める。

判断の軸:

- 壊れる操作をユーザーが実行前に止められること
- 確認の回数が作業の邪魔にならないこと
- ツールを追加したときに権限の決め方が迷子にならないこと

## 理由

- 「読むのは安全、書く・実行するのは危険」という区分は直感に合い、ツール追加時も危険度を 1 つ選ぶだけで済む
- ツール名で個別に判定すると、ツールが増えるたびに判定表の更新漏れが起きる。危険度なら漏れても型（`Risk` の指定漏れ）で気づける
- 拒否を結果として LLM に返すことで、エージェントは代替手段を考えたり、ユーザーに理由を聞いたりと会話を続けられる

## 影響

- メリット
  - 破壊的な操作は必ずユーザーの目を通る
  - 読み取り系は確認なしでサクサク動く
- デメリット
  - 書き込みが続く作業では毎回の y/N が煩わしい（許可の記憶は後続で設計する）
  - 危険度は自己申告なので、ツール実装が危険度を誤って低く申告すると素通りする

## 他に検討した案

- **全部自動許可（v0.1 の固定 Allow のまま）** — エージェントに任意コマンド実行を渡すことになり、個人利用でも事故のリスクが大きすぎるため不採用。
- **全部確認** — 読み取りのたびに手が止まり、エージェントとして使い物にならないため不採用。
- **ツール名ごとの許可リスト** — 柔軟だが v0.2 には過剰で、ツール追加時の更新漏れも起きやすい。ポリシー設定の仕組みを入れるときに再検討する。
